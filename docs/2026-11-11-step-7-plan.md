# Step 7: first real traffic

The treaty plan's last step: **SuperPipeline publishes gate events through the relay, and
AgentPod consumes them. The existing direct push keeps running until this is proven.** It is
done when **a gate decided in chat closes on the board through NATS, end to end on staging.**

The relay (step 6) runs on staging at `staging-relay.superjackfruit.com`, next to NATS.

## What the code already gives us

- **SuperPipeline already has a transactional outbox.** A board's pushes are rows in its own
  SQLite (`push_deliveries`), queued in the same transaction as the change and drained by the
  Durable Object's alarm with retries. So SuperPipeline does not need `treaty-outbox`: the same
  queue gains a second destination.
- **AgentPod already projects a gate idempotently.** `projectGate` answers `already` for a gate it
  has posted, so the hub can receive the same `gate.pending` from the direct push and from the
  relay without posting it twice.
- **The decision travels back unchanged.** A person answers in the room; the hub calls the board's
  decision route as it does today, and the board closes the gate. Step 7 moves the gate's way
  in, not the answer's way back.

## The changes, producer first

| #   | Repo          | Change                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| --- | ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1   | SuperPipeline | When the Worker has `RELAY_URL` and `RELAY_TOKEN` (staging only, at first), every `gate.pending` a board queues gets one more delivery row, for the relay. The drain sends that row as a CloudEvent in HTTP binary mode to `RELAY_URL/v1/events/<subject>` with the producer token, using `treaty-cloudevents`: subject `evt.<tenant>.superpipeline.gate.pending`, type `com.superjackfruit.superpipeline.gate.pending.v1`, `dataschema` from the treaty catalogue, data the same JSON the push carries, and an id fixed per delivery row so a retry is a duplicate at the relay. Everything else about the push is unchanged. |
| 2   | estate        | `310-staging-relay.sh` adds the producer `superpipeline` (token to SuperPipeline's staging env, its SHA-256 to the relay, subjects `evt.*.superpipeline.gate.>`) and the subscriber `agentpod-hub` (`http://hub:3001/public/bridge/superpipeline/events` on the suite-staging network, filter `evt.*.superpipeline.gate.pending`, secret to the hub's staging env).                                                                                                                                                                                                                                                            |
| 3   | AgentPod      | `POST /public/bridge/superpipeline/events` takes the relay's deliveries: verifies `x-treaty-signature` with `verifyDelivery`, decodes the CloudEvent, refuses any type but `gate.pending.v1`, and hands the data to the same projection the push route uses (shared, not copied). It logs the path the gate came by. Fails closed without its secret.                                                                                                                                                                                                                                                                          |
| 4   | staging       | The proof, below.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |

## The proof

On staging, on one board: turn that board's direct `gate.pending` push off, so the gate can reach
chat only through the relay. Open a gate; see it posted in the board's room with the hub's log
naming the relay path; answer it in chat; see the board close the gate. Then turn the direct push
back on. Record it in an estate session.

## Decisions for the operator

1. **Which events go through the relay in step 7.** Proposed: `gate.pending` only, as the plan
   says "gate events". `elicitation.pending` and the record events follow the same path later.
2. **The relay as a deployment setting, not a push config.** Proposed: `RELAY_URL` and
   `RELAY_TOKEN` on the Worker, so every board on a deployment publishes, rather than a push
   config registered on each board.
3. **The workspace in the subject.** Proposed: the board's tenant id, as SuperPipeline knows it.
4. **When the direct push goes.** Not in step 7. After the proof, a later change retires it,
   board by board or all at once.
